# VM100 disk audit: 2026-10-21

## Findings

The temporary restore drill and the nightly GitLab archive made disk usage
look worse than the steady state. The largest current consumers are:

| Path or asset | Approximate size | Decision |
|---|---:|---|
| `/opt/apps/gitlab` | 53 GB | Keep; GitLab data and local native backups |
| `/opt/apps/homelab-backup` | 19 GB before cleanup | Keep active runtime and retained backup runs |
| Docker image/layer storage | 3 GB | No broad prune needed |
| `/var/log/journal` | 1.1 GB | Existing journald retention policy applies |
| Ollama image | 9.18 GB | Keep; used by CouchLoom |
| GitLab image | 6.21 GB | Keep; production GitLab |
| OpenClaw image | 3.91 GB | Keep; production OpenClaw |
| Whiteboard MCP image | 3.89 GB | Keep; production Whiteboard |
| Stirling PDF image | 3.53 GB | Keep; production Stirling |

## Action

After GitLab restore acceptance and its remote post-check passed,
`cleanup-local-runs.sh gitlab` ran with `BACKUP_LOCAL_RUN_KEEP=1`. It removed
only the older `gitlab-20261020-190208` run (about 8.2 GB); the newest
completed run was retained. Incomplete 4 KB marker directories from older
interrupted runs were reviewed separately. Five `database-instance-runtime-*` Ansible
candidate directories from 2026-10-15 were root-owned, unreferenced, and only
148 KB each; they were removed. The newer `client-releases` rollback
directory was retained.

VM100 now reports approximately 37 GB free and 82% used. No volume, database,
registry data, or production image was removed.

## Follow-up

The two unreferenced Whiteboard rollback tags were reviewed against the Pi5
manager service list and removed from VM100; the backend tag released its
73.4 MiB layer and the frontend tag shared layers with another image. The
current data still shows no justification for a broad Docker prune; the
7.437 GiB logical BuildKit cache is recent or referenced.
