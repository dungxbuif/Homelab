# VM100 Production Compute Host

VM100 (`vm100-prod`, `10.10.0.31`) is the current production compute host for
the user-facing workloads migrated off the Mac mini and retired Proxmox K8s
cluster.

## Host

| Field | Value |
|---|---|
| Proxmox VM ID | `100` |
| Hostname | `vm100-prod` |
| LAN IP | `10.10.0.31` |
| vCPU | `6` |
| RAM | `16 GB` |
| Disk | Proxmox `scsi0` 200 GiB per record; ext4 root 194 GiB usable, 65 GiB used / 130 GiB free in 2026-09-16 guest sample |
| Swap | VM100 reports 0 B in 2026-09-16 guest sample; Pi5's recorded swap is separate |
| OS | Ubuntu 22.04 LTS |
| Docker Swarm | Worker in the Pi5-led `homelab-net` Swarm |

VMs `101` and `102` were deleted. Kubernetes and kube-vip residue were removed
from VM100; PostgreSQL remains on Pi5 and was not moved. VM100 joined the
existing Pi5-led Docker Swarm as a worker on 2026-09-12. Production services
were migrated individually to Swarm. The old Compose containers are stopped
and retained only as rollback paths.

Disk was grown online from 80 to 200 GiB on 2026-09-15 without VM restart.
After the 2026-09-15 VM restart, `discard=on` is active. Guest
`sudo fstrim -v /` reported 136.1 GiB trimmed; Proxmox `local-lvm` physical
usage fell from about 83.3 to 66.0 GiB. A pre-restart trim had not reduced
the host pool. See
[GitLab preflight and disk audit](./research/gitlab-vm100-preflight-2026-09-15.md).

Homepage is the first individually verified cutover: its public route now uses
the portless `homepage` Swarm service on `homelab-net`. The old Compose runtime
is retained stopped for rollback after the stability check.

## Routing

Orange Pi `edge_traefik` routes these upstreams to VM100:

```yaml
homepage:  http://tasks.homepage:80
ocr:       http://tasks.macocr-proxy:8080
mezonhook: http://tasks.mezonhook:8080
family:    http://tasks.family-tree:3000
openclaw:  http://tasks.openclaw:18789
n8n:       http://tasks.n8n:5678
mypocket:  http://tasks.mypocket-web:80
netbird:   dashboard http://tasks.netbird-dashboard:80, server http/h2c tasks.netbird-server:80
relayhub:  http://tasks.relayhub:8080
```

Homepage, `openclaw`, `n8n`, and MyPocket now run as Swarm services on
`homelab-net`.
Their public routes use Swarm DNS service names rather than VM100 host ports.
RelayHub follows the same file-provider pattern and Swarm `tasks.*` DNS routing
as the other portless services. The experimental manager-side Docker socket
proxy and Traefik Swarm provider were removed after intermittent overlay
reachability caused public `502` responses.
`bds-app` is intentionally not routed through Orange Pi Traefik. Public ingress
uses the standalone `bds-cloudflared` connector on VM100. The tunnel container
is attached only to the local `bds-tunnel-net` bridge and targets
`http://bds-app:3000`; it must not join `homelab-net`.

## Verification

Homepage cutover was verified on 2026-09-15: both `dungxbuif.com` and
`www.dungxbuif.com` returned 200 through the VPS after the old Compose
container stopped; the Swarm task was healthy, and VM100 had no `18081`
listener. n8n returned 200 and pgAdmin 302 in the cross-route probe. See
[Homepage deployment evidence](./deployments/homepage-2026-09-15.md). Later
cutovers require paired edge-namespace/independent overlay probes if 502 recurs.

MezonHook cutover was verified on 2026-09-15: public 200 after its Compose
container stopped, Swarm task healthy, and no VM100 `18084` listener. A
second edge overlay failure during the canary was localized to unresolved ARP
in the old Traefik task's network namespace; replacing that task restored
cross-route traffic. See [MezonHook deployment evidence](./deployments/mezonhook-2026-09-15.md).

Family Tree cutover was verified on 2026-09-15: public `/login` returned 200
after its Compose container stopped, VM100 port `18085` closed, and the Swarm
task's own DB client returned `SELECT 1`. Source and uploads remain VM100 bind
mounts. See [Family Tree deployment evidence](./deployments/family-tree-2026-09-15.md).

GitLab CE internal deployment was verified on 2026-09-15: `gitlab_gitlab`
task healthy/zero restarts, login 200 through `tasks.gitlab_gitlab:80`, SSH
banner through `:22`, and second `gitlab:check` reported Shell, Gitaly,
Redis, Sidekiq, migrations, and config OK. Its first check had found a
missing Gitaly socket after an overlapping stateful task rollout; restarting
only Gitaly restored it. GitLab uses ~3.05 GiB of its 10 GiB cap in one
sample, VM100 root has ~131 GiB free after installation. A separate VM100
Swarm Rathole client now forwards `tasks.gitlab_gitlab:22` to VPS public
`:2222` over Noise; the public host key matches GitLab's internal ED25519
key. Another portless VM100 Rathole client forwards
`tasks.gitlab_gitlab:80` to an isolated VPS HTTP tunnel; VPS Traefik
temporarily terminates GitLab TLS with a valid Let's Encrypt certificate.
Public login and CSS return 200; direct Orange Pi GitLab still returns 404.
Self-registration is disabled. See [GitLab runbook](./services/gitlab.md).
The bundled Container Registry trial is live on a separate VPS-labeled
domain/tunnel; an ARM64 image push/pull, AMD64 image push, and one-time
backup including Registry layers were verified. Native lab Docker/Swarm
pull still needs a correct internal edge/DNS route, so Pi5 `docker-registry`
remains production. See [Registry trial evidence](./deployments/gitlab-registry-trial-2026-09-16.md).

Do not treat the BDS deployment as a reason to expose databases publicly. The
desired long-term direction for VM100 services is container DNS over
`homelab-net`; Mac-native services remain explicit exceptions when the target is
outside Docker.
All active Swarm services currently share `homelab-net`; a proposed phased
segmentation and the verified network/IP matrix are in
[network audit](./research/network-segmentation-2026-09-15.md). No broad
production network split has been applied.
