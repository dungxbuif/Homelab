# RelayHub full webhook restoration

Date: 2026-10-31. Status: proposed scope and contracts for review; source audit only, no feature tests or deployment run.

Include both inbound webhook-to-agent delivery and outbound signed HTTP callbacks, with endpoint management, routing, retries, DLQ, replay, dashboard and official SDK guidance. The Rust delivery schema currently has `UNIQUE(event_id,generation)` and ties event/app ownership to the target app. Adding fan-out is therefore a storage/authorization change, not just an HTTP worker. This plan isolates that migration and explicitly tests existing quota, gateway, status and response paths.

## Architecture and approach

Chosen proposal: keep the existing PostgreSQL event/delivery authority and extend it with stable target identities and a `sink` (`agent` or `callback`). Reuse fenced state transitions and outbox/recovery paths; a callback worker claims only callback deliveries, while gateways claim only agent deliveries. This preserves one audit/replay model. A separate callback database/queue would duplicate acceptance, quota and replay logic; direct best-effort POST after ingress would lose durability.

Routes resolve once inside acceptance and become immutable delivery targets. The source event is unchanged by retries/replay. Rule changes affect new publications only. Endpoint's original agent target stays the sole sync response source; additional routed targets run asynchronously and cannot answer that request. Existing single-delivery receipts/status retain their primary-target meaning; an additive target-list endpoint exposes fan-out.

## Exact proposed contracts

- PostgreSQL acceptance, quota charge, target deliveries and outbox commit atomically before `202`. At least once; receivers deduplicate effects by event ID plus target identity. No exactly-once promise.
- Preserve v1 body maximum 1 MiB, seven-day event retention, 10,000 outstanding deliveries and 100 MiB outstanding payload bytes per workspace. Charge bytes once per outstanding target delivery, matching current per-delivery accounting.
- Preserve sync timeout default 15 seconds, allowed 1–30 seconds; offline `queue` → `202`, `reject` → `503` without acceptance; timeout `continue` → `202`, `expire_pending` → `504` with only unclaimed primary work canceled. Claimed work may finish; an HTTP timeout does not prove cancellation.
- Endpoint auth remains explicit public or shared bearer. New bearer secret is displayed once and stored hashed; rotation immediately rejects the old secret for new ingress. Disabled/archived endpoints accept no new requests; accepted deliveries retain their immutable configuration snapshot. Archive is a tombstone, not destructive deletion of history. Endpoint policy updates use a revision precondition to prevent lost updates.
- Each app has at most one outbound callback configuration (URL, enabled state, revision and signing-key versions), consistent with the original Go app model. It belongs to the target app, not to an ingress endpoint. Multiple ingress endpoints may route to that app; multiple distinct callback URLs require separate target apps in this release.
- Callback URL is HTTPS with default/explicit port 443, no userinfo/fragment. Disable redirects and environment proxies. Resolve/check every destination and reject private, loopback, link-local, metadata, multicast and non-global addresses, including IPv6/mapped forms; pin the validated addresses for that attempt while preserving TLS hostname checks. Local/LAN apps use the outbound agent path. HTTP is permitted only inside disposable tests with an injected transport, never as a production config shortcut.
- Callback HTTP method is POST, timeout 10 seconds, response read cap 1 MiB. Success is `2xx`; retry network errors, `408`, `425`, `429`, `5xx`; all other responses, including redirects, become terminal DLQ reasons. Five attempts total with base delays `1,5,30,120` seconds, matching v1. For `429`, valid `Retry-After` seconds/date overrides the next delay clamped to 1–300 seconds; invalid hints use the base delay. Never retry past event retention.
- Callback body is a versioned JSON envelope with event/delivery/target IDs, generation, source app, event type, creation time and the original request (`method`, `path`, safe ordered headers, base64 body). Store exact serialized callback body bytes per delivery generation; a retry signs those same bytes with a fresh timestamp.
- Forwarded request headers use existing `webhooks::safe_headers(headers, true)`: case-insensitively remove `connection`, every header named by its comma-separated tokens, `keep-alive`, `proxy-authenticate`, `proxy-authorization`, `te`, `trailer`, `transfer-encoding`, `upgrade`, `content-length`, `authorization`, `host`, `cookie`, `x-csrf-token`, `x-api-key`, `idempotency-key`, `forwarded`, `x-real-ip`, `x-forwarded-*`, and `x-relayhub-*`. Preserve order and duplicates for remaining headers. The same filter applies to SDK-published request envelopes before routing; it is not just an ingress HTTP filter. Remaining caller-provided headers are application payload, not proof of caller identity or local-service credentials.
- Signing matches the existing primitive: lowercase hex HMAC-SHA256 over `timestamp + "\nPOST\n" + request_target + "\n" + lowercase_hex(SHA256(raw_callback_body))`. Request target is the exact escaped path plus query, not a decoded/reordered URL. Headers: `X-RelayHub-Timestamp`, `X-RelayHub-Signature`, `X-RelayHub-Event-Id`, `X-RelayHub-Delivery-Id`, `X-RelayHub-Key-Id`. IDs must also be inside the signed body. SDK verification uses constant-time comparison and default timestamp tolerance 300 seconds; receiver effect deduplication is still required.
- Callback signing secrets must be recoverable for sending: encrypt them in PostgreSQL with a versioned operator key loaded from a Swarm secret, using a maintained authenticated-encryption library. Hash-only storage cannot sign callbacks. Never return plaintext after creation/rotation or log it. Pin signing/config versions per delivery generation; rotation affects new deliveries. Retiring a compromised key sends its unclaimed pending/retrying deliveries to DLQ with `key_retired`; it prevents new claims but cannot undo an already emitted HTTP effect. An owner may replay these only with an explicit enabled replacement callback config revision, recorded in the new generation and audit. Existing event and target identity stay unchanged. Retain required encrypted key versions through event retention, and back up operator key material separately in 1Password. No automatic rekey/secret destruction during this work.
- Routing rule: workspace, optional source app, event type exact match or `*`, target app, sink and enabled flag. No cross-workspace routing. Maximum 32 unique targets per event, deduplicated by `(target_app,sink)`; reject overflow before commit. Existing primary agent target is always present. No client-provided arbitrary destination URL and no payload transform runtime.
- Replay is owner/admin-only, allowed only from retained `dlq` delivery state, with UUID request ID. Same actor/workspace/request ID and same selected delivery IDs/config revisions returns the original result; different content under that ID conflicts. Batch contains 1–100 distinct explicit IDs, validated atomically; no implicit replay-all. A new generation is per immutable target, not per event globally. Old leases cannot settle it. Succeeded/cancelled/expired deliveries cannot replay. By default preserve the original callback config; an optional explicit per-target replacement revision must belong to the same target app and be enabled with a non-retired key. Plain replay cannot bypass a disabled/retired config.
- Attempt/audit metadata includes safe reason/status/duration/IDs and actor; no plaintext secret, callback URL query, raw auth/header material or payload in list/timeline logs. Payload inspection, if exposed, is a separate authorized detail action under retention controls.

## Boundaries

Provider-specific inbound signatures were deferred in the Rust baseline and are not silently implemented as generic HMAC: each provider has its own contract. Full TCP tunneling, website proxying, remote functions, generic payload transforms, billing and public signup remain separate product scope. The existing bearer/public ingress plus outbound RelayHub signature helpers are concrete deliverables here.
